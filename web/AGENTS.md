# Web UI (`web/`)

Local-only web app at `http://127.0.0.1:4323`. Astro in server mode. It reads repo files on every request and holds no state. Install, start, and uninstall: [`docs/install/web-ui.md`](../docs/install/web-ui.md).

## Hard rules

1. **Pages never read files.** A page imports from `src/lib/` and `src/components/` only. All disk access lives in `src/lib/repo.ts` (NDJSON, YAML, markdown). No `readFileSync` in a `.astro` file.
2. **No rule is computed in TypeScript.** Habit rates, traffic lights, sleep-lever values, project velocity, days idle, focus status, and the slipping list come from Python through `src/lib/computed.ts`, which runs a script and parses its JSON. Project velocity and days idle live in `automations/scripts/project_gauges.py`, the one home for those two rules; `home_data.py` reads days idle (the stalled-project row under What needs you) and puts velocity and days idle on its active project rows. Any other reader calls the same two functions, so two surfaces cannot disagree. If a page needs a new number with a rule behind it, add it to `automations/scripts/home_data.py` with a pytest first. `src/lib/priority.ts`, `src/lib/sort.ts`, and `src/lib/format.ts` reshape, order, reword, and format stored fields only; they decide nothing.
3. **Python runs as `PFC_PYTHON`.** `computed.ts` reads `process.env.PFC_PYTHON || 'python3'`. The scripts need PyYAML (`automations/requirements.txt`), so point `PFC_PYTHON` at an interpreter that has it; the launch agent sets it. A panel that renders `Could not load this panel.` almost always means this variable points at the wrong interpreter.
4. **Wrap every Python call in `safe()`** from `src/lib/safe.ts`, and render the failure as `<p class="muted">Could not load this panel.</p>` plus a `<details>` holding the error. One broken script must degrade one panel, not blank the page. `web/test/smoke.sh` fails when that sentence appears on `/`.
   A failure that is not a panel's own, such as one bad line in an NDJSON file, reaches `src/pages/500.astro`. That page prints the error's message, never its stack, and one line saying a named file and line number means that line is not valid JSON. It uses the `Base` layout, which is safe because `Base` reads no file, so the error page cannot throw an error of its own.
5. **One call per script per page render.** Each call starts a Python process. Call `getHome` or `getSlipping` once in the frontmatter and read the result from there.
6. **Pages never write to the repo.** Two kinds of route lead to a write: `POST /api/chat`, which starts `claude` in auto mode (see Chat below), and the twelve `POST /api/write/*` routes, which start `automations/scripts/web_write.py` through `src/lib/write.ts` (see Writes below). Nothing else writes.
7. **Every NDJSON data file is shown on the home page or listed in `AGENT_ONLY_DATA`.** `src/lib/data-files.ts` holds both lists (`HOME_DATA` and `AGENT_ONLY_DATA`), and `test/data-files.test.ts` fails when a data file is in neither, in both, or listed but missing. Findings, hypotheses and insights are agent-only: no page shows them, and the agent raises one in chat when it applies to what you are doing. When you add a data file, add it to one list.
8. **Display rules from the root `AGENTS.md` apply.** Higher is better on every metric, red first in color-coded lists (`byLight` in `src/lib/sort.ts`), 12-hour times, local dates from `src/lib/dates.ts`, Solarized Light only.
9. **Records are named, not numbered.** Show a title. An id may appear in three places and nowhere else: a `title=""` tooltip, an `id=""` anchor, and inside a chat prompt a button puts in the drawer's box, where it tells Claude exactly which record is meant.
10. **Habits show `title`, not `description`.** The home page shows `title_plain`, the same name with acronyms spelled out (`home_data.HABIT_PLAIN`). `title` is the short name; `description` runs to a paragraph and belongs in a `title=""` tooltip.
11. **Text is the palette's dark tone.** Body text is `var(--ink)` (`#073642`, 12:1 on the ground); the Solarized mid greys fail 4.5:1 there and are not used for text. Secondary text that carries information uses `.sub` (`var(--sub)`, about 6:1). `.muted` is for empty-state messages and minor labels only, never for a reason, a rate, or a date. A status word uses the darker `--red-t` / `--yellow-t` / `--green-t`; the plain status colors are for fills and shapes. A status is a shape, a color and a word (`Light.astro`: square red, triangle yellow, circle green).
12. **Three kinds of button.** Filled (`.btn-primary`, or the first pick's Done): the one main action of a card. Outlined in ink (`.act-write`): changes the repo now. Underlined blue (`data-chat-prompt`): puts a prompt in the chat box and waits there.
13. **Bind to `127.0.0.1` only.**
14. **One Content-Security-Policy, sent twice.** The directives live once in `src/lib/csp.ts`. `src/layouts/Base.astro` puts `META_POLICY` in a meta tag, and `src/middleware.ts` sends `HEADER_POLICY` as a real response header on every response, pages and API routes alike, together with `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`. The header copy adds `frame-ancestors 'none'`, which a browser ignores inside a meta tag, because a framed chat panel is a clickjacking target. The policy allows `'self'` plus inline styles and inline scripts, images from this server only (no `data:`), no `<base>` target, and forms only to this site. When you add an external resource of any kind, a font, a script, a stylesheet, an image host, or a request the page makes, add its origin to the matching directive in `csp.ts`, then load the page in a browser and read the console: a blocked resource is reported there as a Content-Security-Policy violation and silently does nothing otherwise. Prefer bundling the file into the app over widening the policy. `web/test/smoke.sh` checks the first two headers on `/` and on `/api/chat/skills`.

## Home page

`/` (`src/pages/index.astro`) is one page of eleven `<section data-band>` bands (`src/components/Band.astro`) in three groups by how far ahead each looks, each with a `.zone-head` label:

| Group | Bands |
|---|---|
| **Today** | Body first, The 2+1, Habits, Week |
| **This quarter** | Focuses, Projects, Trends |
| **Always** | Areas, Values, Visions, Front of mind |

Quick add sits under the last group. Everything the page shows comes from one `getHome()` call (`automations/scripts/home_data.py`); the page only words and lays out what it is handed.

The optional reMarkable pages (`automations/scripts/remarkable_pages.py`, [`docs/remarkable.md`](../docs/remarkable.md)) draw the same three groups from the same `build_home` dict. A band added, removed or reordered here gets the same change there.

- **What you act on today comes first.** Sets that rarely change (household rooms, a day's later events) sit folded in a `<details>` with a count in its summary, and open by themselves when something in them needs a look.
- **Body first** is a dark strip with the sleep verdict, tonight's move, hours slept and minutes awake, beside last night's sleep levers folded in a `<details>` whose summary counts them by light. The summary names the levers red last night that are not usually red. A lever shows `label_plain` (acronyms spelled out) and `target_words` (the target in words, not `<=`).
- **Long-running reds fold.** A red that has held two weeks or more (`chronic`, `home_data.CHRONIC_DAYS`: a focus red 2+ weeks, a project idle 28+ days, a lever red on at least half of the last 14 nights) folds into one line right after the worst of its group (`chronic_lead`), which keeps its own row. A red that is not long-running keeps its own row, so a new red stands out. `FocusMeter`, `ProjectRow` and `LeverRow` are the rows, shared by the list and the fold.
- **The rating card.** While the day Python names is unrated (`rate_target`: yesterday before about 6 PM, today after), a `How was yesterday?` card sits under Body first with energy, mood, focus, and the optional hyperfocused answer.
- **The 2+1** opens with a `Why` line (the focus of the day, its vision and value). It shows today's picks all day, with their Done buttons. From about 6 PM it also shows tomorrow's picks, or the suggestions for `pick_date` while none are set (always three, a full 2+1), each with Set, Already done (`complete-task`) and Pick another (`skip-suggestion` for that day). Before 6 PM, once every critical pick for today is done (`all_picks_done`), the suggestions show again under the done picks and Set adds one or two to today's picks, sending the stored ids back with the new ones (`appendPicksRequest` in `src/lib/day.ts`). The rating and the picks are posted by `src/scripts/day-client.ts`, with the request bodies built in `src/lib/day.ts`.
- **What needs you** comes before `An agent can do these`. It lists the overdue and flagged items, at most one due rolling review with a `Start this review` link to `/review`, and the one thing Python says to look at (`tour_look`: a stale life wheel, a red focus or a stalled project). A row Python tags `in_picks` is left out, and that pick's card shows the row's deadline as its `flag` instead, so one task never has two Done buttons.
- **Habits** lists only the daily habits logged by hand and not yet logged today, each with one `Log today`. The logged and automatic daily habits, the monthly habits, and `Log yesterday` (every hand-logged habit not logged yesterday) each sit in a folded `<details>` with a count.
- **Areas** opens with the plate (committed hours this week against free waking hours, `plate`), then lists each life-wheel area collapsed to its light and weekly hours. Its `<details>` opens the area's items (light, Time or Status, hours, weight, and why) and the manual G / Y / R light, which counts only while no item has data. Every light and hour there comes from `automations/scripts/area_items.py`; the household rooms keep their own manual lights.
- **One-tap changes with fixed values write in place:** area and room lights and notes (G / Y / R plus a note and Save, `src/scripts/home-client.ts`, posting `set-area` or `set-room` once), Park / Unpark on focuses, Park / Activate on projects, Retire on an anchor. Anything that needs wording opens the chat with a `chatPrompt` template. The page itself is the daily routine, read top to bottom.

The header holds three tabs, Now, Tasks and Review, plus `Stuck` and Chat.

The **Tasks** tab (`src/pages/tasks.astro`) is a list of cards: priority code, title, area, size, project, agent, deadline and age. The Project filter also offers `Not in a project`. A row's buttons are `Pull into today` or `Hand to agent` filled, `Done` outlined, `Done in chat` and `Drop` quiet. It sorts by priority, deadline, area, size or age in the browser over the fields the server wrote (`sortTaskRows` in `src/lib/sort.ts`). Pull into today posts `set-picks` for today with the picks already set (done ones included) plus that task, and refuses when two picks are still open (`pullIntoToday` in `src/lib/write-ui.ts`).

## Review page

`/review` (`src/pages/review.astro`) is the one place reviews happen on the web. Reviews run one at a time, so it shows the same review `/pfc-review` and the reMarkable `4 - Review` page would: one `getReview()` call (`web_data.py --review`, which is `review_forms.current_review`), or `No reviews due right now.` when that is null.

- It shows the label, how overdue (`reviewDue` in `src/lib/review.ts`: never done, due today, or N days overdue) with the form's intro, and `N reviews due; one at a time.`
- Each `choices` section is a list of rows with one tap chip per option (one option per row, tap again to clear) and a one-line note box when the section has `note`; a section with no options is answered by the note alone. Each `prompt` is a textarea `lines` tall.
- Every change rebuilds the answers (`buildAnswers`, blanks left out) and writes `/pfc-review <id> answers <json>` (`PROMPTS.reviewAnswers` through `answersPrompt`) onto `Save answers`' `data-chat-prompt`, so the drawer's own click handler puts it in the box. Save is disabled while nothing is answered. Pressing Send has `/pfc-review` apply the answers and stamp the review; a reload then shows the next one.
- `Skip this review` posts the `stamp-review` write and reloads onto the next due review. The home page's due review only links here.

## Chat

The drawer on every page (`src/components/ChatDrawer.astro`, `src/scripts/chat-client.ts`) talks to `src/pages/api/chat/`. Its `Hide` button only slides it away: the conversation and any running reply stay, and while a conversation exists a `Chat` tab on the right edge brings it back. On screens 1100px and wider the page narrows beside the open drawer (`html.chat-docked`), so the page stays readable; an inline script in `Base.astro` sets that class before the first paint. `POST /api/chat` starts a process that can edit and commit in this repo, so these rules are hard:

1. **Only this app's pages may start a run.** `checkRequest` in `src/lib/chat/guard.ts` refuses with 403, and starts nothing, unless: `Host` is `127.0.0.1:<port>` or `localhost:<port>` for the port the server was started on; `Origin`, when present, is `http://` on one of those two; `Sec-Fetch-Site`, when present, is `same-origin` or `none`; and the header `X-PFC-Chat: 1` is present, which forces a cross-origin preflight this server never approves. The stop and attach routes run the same header checks.
2. **No shell.** `spawn(PFC_CLAUDE, args)` only, with the repo as the working directory. The child's environment is the server's plus `PFC_WEB_CHAT=1`, so a skill started from the drawer knows not to open a second copy of the page. The message is the last argv element, after `--`, so nothing in it is ever read as an option (`src/lib/chat/args.ts`).
3. **`--permission-mode auto` and `--permission-prompts none`, always.** Auto mode keeps the allow list from growing one refused command at a time: Claude Code's classifier approves routine actions and blocks risky ones, allow and deny rules still apply, and whatever it blocks comes back as a refusal the drawer shows. Never use `bypassPermissions` or `--dangerously-skip-permissions`, and never let the message change the mode (`test/chat-args.test.ts`). An agent session running in auto mode is blocked from editing this flag, because that widens its own permissions; a change to it is yours to make by hand. Skill commands that use `$(...)` run because of the repo's `PreToolUse` hook, `scripts/hook-allow-known-commands.py`, which allows a command only when every command word in it is already on the allow list, no deny or ask rule in any settings file matches, and its redirects stay inside the repo (`docs/conventions.md` § "Bash permission hook").
4. **Only sessions this server started may be resumed.** Their ids are kept in `web/.chat-sessions.json` (ignored by git). A well formed id that is not in that file is refused, because every Claude Code conversation on the machine has one.
5. **One live run per session, three across the server.** A second message to a busy conversation gets 409, a fourth run gets 429. Only live runs count: a finished run kept for its grace period (rule 12) counts toward neither. A run stops only on the stop route, after 30 minutes, or when the server exits; a page going away does not stop it.
6. **Error text sent to the browser is fixed wording.** The real detail, which can name a path or an environment value, goes to the server log, `/tmp/pfc-web.log`, on a `[pfc-chat]` line.
7. **A prompt that names a record is never sent by itself.** A page button carries `data-chat-prompt` and must be a real `<button type="button">`: the client acts only on a button or `role="button"`, never on a click that landed on a link. Its text is placed in the box and waits for Send. Only a bare slash command whose button also carries `data-chat-send="1"` sends at once (`promptAction` in `src/lib/chat/input.ts`). Write prompts through `chatPrompt` and the templates in `src/lib/chat/prompts.ts`, never by joining strings in a page.
8. **Assistant text is sanitized before it enters the page.** Markdown goes through DOMPurify in `src/lib/chat/markdown.ts` with its `FORBID_TAGS` and `FORBID_ATTR` lists (no `style`, `class`, `id`, `name`, `src`, `srcset`, `background`, `formaction`, `ping`, and no data attributes), so a reply cannot draw itself a refusal box or take over an id the drawer uses. Tool output is shown as plain text only.
9. **The response headers come from `src/middleware.ts`,** with the policy string shared with the meta tag through `src/lib/csp.ts` (hard rule 14).
10. **The page goes in the system prompt.** The client sends `page` (the page's title and path); the guard keeps it only when it is plain text of at most `PAGE_LIMIT` characters with no control characters, and `buildArgs` passes it as `--append-system-prompt` before `--`, never inside the message, so a slash command still reaches its skill unchanged.
11. **Tests never start the real claude.** Unit and route tests use `web/test/fixtures/fake_claude.sh` through `PFC_CLAUDE`. A real run spends your subscription quota.
12. **A reply outlives the page, and messages queue.** `src/lib/chat/runner.ts` keeps every event of a run in one numbered log (capped at 5,000 events, text dropped past that), and any number of readers read it from an index. `src/lib/chat/stream.ts` writes it as server-sent events, each event frame carrying its number in `id:`, for both `POST /api/chat` and `POST /api/chat/attach`. Attach takes `{ "id": <run id>, "from": <first event wanted> }`, runs `checkHeaders` (403), refuses a malformed id or index with 400, and answers 404 `That reply is no longer available.` for a run it does not have. A finished run stays readable for 10 minutes (`PFC_CHAT_KEEP_MS`), then is forgotten. The client saves the run id and the last applied event number with the transcript in sessionStorage (`src/lib/chat/resume.ts`), attaches again on load and on a return from the back-forward cache, and writes no ending on `pagehide`. Send while a reply is running adds the message to a queue above the box (`src/lib/chat/queue.ts`, kept in sessionStorage, 20 at most); when the reply ends on its own the first one is sent into the same conversation, while after Stop the queue waits for Send next or an empty Send. New chat clears the queue. The queue is client-side only, so the 409 in rule 5 still stands.

## Writes

The `Done`, `Drop`, `Log today`, `Log yesterday`, and `Park` / `Unpark` buttons (`src/components/ActionButton.astro`, `src/scripts/write-client.ts`) post to `src/pages/api/write/`, and so do the day rating and the 2+1 picks (`rate-day.ts`, `set-picks.ts`), the Review page's Skip (`stamp-review.ts`), and the home page's other one-tap writes (`skip-suggestion.ts`, `set-area.ts`, `set-room.ts`, `retire-anchor.ts`, `set-project.ts`). These rules are hard:

1. **One writer.** Every direct edit is `automations/scripts/web_write.py`, and it has twelve actions:

   | Action | Arguments | What it does |
   |---|---|---|
   | `complete-task` | `<task_id>` | Marks the task done. |
   | `drop-task` | `<task_id>` | An open task you decided not to do: the record is removed from `tasks.ndjson` and a `deleted` event is logged, the same way a drop made in chat is recorded. A task some 2+1 record names moves to `tasks-archive.ndjson` with `dropped: <date>` instead, because every pick must still resolve. A done task is refused. |
   | `log-habit` | `<habit_id> [YYYY-MM-DD]` | Today when no day is named. A named day must be today or one of the `LOG_WINDOW_DAYS` = 7 days before it (`pfc_writes.py`). Cadence comes from `config/habit_schema.yaml`, so a monthly habit goes to the monthly log. Refused for `auto_derived` habits. |
   | `park-focus` | `<focus_id> on\|off` | Parks or unparks a focus. |
   | `rate-day` | `<YYYY-MM-DD> <energy> <mood> <focus> [hyper:yes\|no]` | Rates today or yesterday; refuses a day that is already rated. |
   | `set-picks` | `<YYYY-MM-DD> <task_id>... [bonus:<task_id>]` | Today or tomorrow. A critical id already in that day's `completed` stays a done pick, at most two critical ids may be undone, and every other pick must be an open task that no agent can finish and that is not deferred. |
   | `stamp-review` | `<review_id>` | Marks a rolling review done today. |
   | `skip-suggestion` | `<YYYY-MM-DD> <task_id>` | Today or tomorrow, an open task: adds the id to that date's `skipped` list in `daily-focus.ndjson`, creating a record with no picks when the date has none. `home_data.suggest(day)` reads the same list. |
   | `set-area` / `set-room` | `<key> green\|yellow\|red [note:<text>]` | The key must exist in the newest snapshot of `life-wheel.ndjson` or `household-status.ndjson`. A snapshot dated today, with `logged_at` set to now with its local offset, is appended, copying every other rating and note from the newest row; a second change on the same day edits that day's snapshot, because the readers take the newest date and a tie would pick the older row. |
   | `retire-anchor` | `<ground_id>` | A Front-of-Mind anchor in `data/grounding.ndjson` gets `status: "retired"` and `retired_date` today. |
   | `set-project` | `<proj_id> active\|parked` | Sets `active` and `status` together. It only switches between those two, so a `done` or `dropped` project is refused. |

   The `note:<text>` argument is one argv element, `note:` plus the text, never split: one line of at most 300 characters (a newline or other control character, or more characters, is refused with 400). Empty text after `note:` clears the key's note; with no note argument the note stays.

   The routes map their JSON bodies to those argument forms after checking the shapes (ratings are integers 1 to 5; one to eight critical ids, because the done picks travel with the new ones and the writer holds the cap of two open picks; a review id of the habit-id shape; area and room keys of `^[a-z][a-z_]{0,31}$`; a light of green, yellow, or red; anchor ids `ground-YYYYMMDD-NNN`; project ids `proj-YYYYMMDD-NNN`), so a bad body never starts the writer.

   `src/lib/write.ts` only spawns it (argv array, no shell, repo as working directory, 120-second limit, one write at a time server-wide: a write that arrives while another runs waits its turn, so you can click down a list without waiting between clicks; past `MAX_PENDING` = 20 waiting or running the next gets 409 `Too many changes are waiting to be saved. Try again in a minute.`) and maps its exit code to a status. On the page only the clicked row's buttons are disabled while it saves, and the page reloads once every click has its answer. The record changes themselves live in `automations/scripts/pfc_writes.py`. No rule is written in TypeScript.
2. **The same guard as the chat.** Each route runs `checkHeaders` from `src/lib/chat/guard.ts` (called in `src/lib/chat/write-request.ts`) (Host, Origin, `X-PFC-Chat: 1`, `Sec-Fetch-Site`), requires `Content-Type: application/json` and a body of at most 4 KB, and checks the id's shape before anything starts: `^task-\d{8}-\d{3}$`, `^[a-z0-9][a-z0-9-]{0,63}$` for habits (no leading hyphen, so an id can never read as a flag), `^focus-\d{8}-\d{3}$`. A habit log's optional `date` must be a real calendar date written `YYYY-MM-DD` (`isIsoDate` in `src/lib/dates.ts`), so it can never read as a flag either. A failed check returns 400, 403, 413, or 415 and starts nothing.
3. **The lock and the accepted race.** The writer holds an exclusive `flock` on `data/.web-write.lock` (git-ignored) for the whole read, change, write, commit, and push; a second writer gets exit 3 `Another change is still being saved.` Skills write with their own `jq` temp file and take no lock. That race is accepted for one user, with two guards: the writer refuses (exit 3, `dirty`) when a file it needs has uncommitted edits, and it re-reads each file just before replacing it and refuses (exit 3, `changed_underneath`) when the bytes changed since it read them.
4. **The branch guard.** A real write refuses with exit 3 `The repo is on branch <name>, not main; nothing was changed.` unless the checkout is on `PFC_WRITE_BRANCH` (default `main`). A detached HEAD is refused too (`The repo has no branch checked out.`).
5. **Commits follow the repo conventions.** Subjects are `task: complete <description>`, `task: drop <description>`, `habit: log <YYYY-MM-DD>`, `focus: park <title>`, `focus: unpark <title>`, `track: log day <YYYY-MM-DD>` (rate-day), `focus: set <YYYY-MM-DD>` (set-picks), `review: stamp <label>` (stamp-review), `focus: skip <title>` (skip-suggestion), `review: area <label> <light>` (set-area), `review: room <label> <light>` (set-room), `grounding: retire <title>` (retire-anchor), and `project: activate <name>` or `project: park <name>` (set-project); the body is `Written by the web UI.` and the trailer `Co-Authored-By: PFC web UI <noreply@localhost>`. Only the changed paths are committed, so anything else staged stays out. The pre-commit hook runs `scripts/validate.sh`; the writer does not run it a second time, so `.git/hooks/pre-commit` must be installed (root `AGENTS.md` § Repo validation). A real write refuses with exit 3 `The repo's pre-commit hook is not installed; see docs/install/web-ui.md.` when `git rev-parse --git-path hooks/pre-commit` is not an executable file. A refused commit restores the files from HEAD and exits 4 with the validator's first failure line.
6. **Push.** `git push` runs with a 30-second limit. When it fails, the commit stands, the JSON says `"pushed": false` with the first line of git's error, and the page says `Saved. Not pushed yet.` The same happens when the writer is stopped by `SIGTERM` after the commit exists. Stopped before the commit, it restores the files and nothing is saved.
7. **Push authentication.** When `PFC_PUSH_GH_USER` is set (for a machine whose active `gh` account is not the one that can push this repo), the writer runs `git -c credential.helper= push origin <write branch>` with `GIT_ASKPASS` pointed at a temporary helper that answers with that user name and `gh auth token --user <name>`. The token is read from the gh keyring per push and nothing is written to disk or git config; the helper file holds no token and is deleted after the push. When `gh` is not on `PATH`, the push is skipped with `gh is not on PATH; cannot read the push token.` Unset, the push uses git's normal credentials.
8. **Trello.** The commit runs with `PFC_SKIP_TRELLO_RENDER=1`; after the push the writer starts `trello_render.py` detached, output appended to `/tmp/pfc-web.log`, and returns without waiting. `--no-render` skips it.
9. **Line format.** Files are rewritten through `automations/scripts/ndjson_file.py`: untouched lines keep their exact bytes, and a changed or new line is written the way `jq -c` writes it.
10. **A missed habit can be marked done.** A habit logged as missed (in chat, say) can be marked done from the page: `log_habit` updates that row in place instead of adding a second one.
11. **Monthly habits.** The validator and both writers keep one row per habit per date, while `pfc-log-habit` describes monthly habits as one row per month, so a monthly habit can have several rows in one month.

Run the writer by hand from the repo root. `--dry-run` takes no lock, writes nothing, and prints what it would commit:

```bash
python3 automations/scripts/web_write.py --dry-run complete-task <task_id>
```

Tests: `automations/scripts/tests/test_web_write.py` builds a throwaway git repo per test, and `web/test/fixtures/fake_web_write.sh` stands in for the writer in the route tests. No test writes the real data files.

## Working on it

- Tests: `cd web && npm test`. One file: `npx vitest run test/sort.test.ts`.
- Types: `cd web && npm run check`. Zero errors, warnings, and hints.
- All routes: `web/test/smoke.sh`. It builds, serves on port 4399, checks that `/`, `/tasks` and `/review` answer, checks the chat and write routes, and stops its own server.
- Dev server with reload: `cd web && npm run dev`. It serves on port 4324 and sets `PORT=4324`, because the chat endpoints compare the request's `Host` against `PORT` and would refuse every chat request with 403 if the dev server moved to a port they did not know.
- **Stop a test server by port, never by name.** `kill $(lsof -tiTCP:4323 -sTCP:LISTEN)`. A name pattern such as `pkill -f 'dist/server/entry.mjs'` can also match an unrelated server on the same machine.
- **The launch agent updates itself; no restart is needed after a code change.** `automations/scripts/run-web.sh` checks every 20 seconds (`PFC_WEB_CHECK_SECONDS`) whether anything under `web/src`, `web/public`, `astro.config.mjs`, `package.json` or `package-lock.json` is newer than the build it serves. When it is, it builds into `dist-next` while the old build keeps serving, waits until `GET /api/build` reports `busy: false` (no live chat run, no write running or queued: `serverBusy` in `src/lib/build.ts`), then stops the server, swaps `dist-next` in, and starts it again. A failed build leaves the old one serving and is not retried until the source changes again (stamp `web/.dist-failed`). A changed `package-lock.json` instead makes the script exit once idle, so the launch agent starts it again and the startup `npm ci` runs. `web/test/autoupdate.sh` checks all of this on port 4397 with its own build folder.
- **Open pages reload themselves onto the new build.** Every build gets an id (`__PFC_BUILD_ID__` in `astro.config.mjs`), which `Base.astro` puts on `<html data-build>` and `GET /api/build` reports. `src/scripts/update-client.ts` asks every 15 seconds and when the tab comes back into view, and reloads when the id differs (`updateStep` in `src/lib/update-step.ts`). A failed request is not a reason to reload. While a text field holds unsent text it shows a note with `Reload now` instead.
- Restarting the launch agent by hand (for example after changing `run-web.sh` itself, which the running script does not reread) and reloading its plist: [`docs/install/web-ui.md`](../docs/install/web-ui.md).
- Check every page change in a real browser before calling it done. A passing test shows the data is parsed correctly, not that the page reads well.
- Logs: `/tmp/pfc-web.log`.
